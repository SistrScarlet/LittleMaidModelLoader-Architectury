# LMML 1.21.1 移植計画

## 概要

LMML を Minecraft 1.20.1 (8.3.1) から 1.21.1 (9.0.0) へ移植する。
既存の `local/1.21` (10.0.0-alpha2, MC 1.21) は forge/neoforge 両在・破棄予定の派生ブランチのため参考程度に留め、`1.20` ベースで再出発する。

本タスクは [LMRB 1.21.1 移植計画](../../../LittleMaidReBirth-Architectury/docs/plan/2026-06-06_lmrb-1.21.1-migration.md) のフェーズ 0 (前提) に位置する。

## 確定方針

| 項目 | 決定 |
|------|------|
| ターゲット MC | 1.21.1 ピン留め (Stonecutter 不採用) |
| プラットフォーム | fabric + neoforge (forge は切る) |
| ベースブランチ | `1.20` |
| 移植先ブランチ | `1.21.1` |
| バージョン | `9.0.0` |
| 旧 `local/1.21` | 破棄 (10.0.0-alpha2 の採番は不採用) |
| 1.20 ブランチ | 並行開発を継続。1.21.1 への反映は cherry-pick 運用 |
| 作業順序 | LMML 1.21.1 → LMRB 1.21.1 → LMRBCompat 1.21.1 (直列) |
| Network パケット | Architectury NetworkManager で抽象化 |
| Model パック互換性 | 既存 .class ベースのモデルパックを動かす設計を維持。Java 21 / 新 ClassLoader 制約下で要検証 |

## LMML 固有の重大ポイント

LMRB と異なり、LMML 移植の難所はモデル/リソース系に集中する:

1. **MultiModelClassLoader / MultiModelClassTransformer (合計 450 行)**
   - 旧 LittleMaid (Forge 製) 時代の .class モデルパックを動的ロード/変換する独自実装
   - Java 21 + 新 ClassLoader 制約 (sealed class, restricted module access) で動くか要検証
   - ASM のバージョン (Minecraft バンドル品) が 9.x になり一部 API 変更の可能性
2. **Renderer 系の API 追従 (大物)**
   - `MultiModelRenderer`, `MultiModelArmorLayer`, `MultiModelHeldItemLayer`, `MultiModelLightLayer`, `MultiModelRenderLayer`
   - `VertexConsumer.addVertex()` / `BufferBuilder` → `MeshData` / ARGB int tint 化
   - `MMVertexConsumer`, `MMRenderContext`, `MMMatrixStack`, `MMPose` の抽象層も追従が必要
3. **ResourcePackManagerMixin (fabric)**
   - 1.20.5 で `ResourcePackManager` 周辺が再設計された影響を直撃する可能性
   - `LMPackProvider` 側の API も同時に追従
4. **モデル/サウンドパックの読み込み**
   - `LMSoundLoader`, `LMMultiModelLoader`, `LMTextureLoader` 等
   - `ResourceManager` / `ResourceReloader` API 変更追従

## 作業フェーズ

### フェーズ 1: ビルド環境セットアップ

- `1.20` から `1.21.1` ブランチを切る
- `gradle.properties` / `settings.gradle` / Architectury Loom plugin 更新
- `forge/` → `neoforge/` リネーム + プラットフォーム実装書き換え
- Java 17 → Java 21 切り替え
- ビルド通過まで持っていく (コンパイルエラーは次フェーズで順次解消)

### フェーズ 2: バニラ API 追従 (大物)

優先度順:

1. **Identifier**: `new Identifier(...)` → `Identifier.of(...)` 一斉置換
2. **Renderer 系** (LMML 最大の工数)
   - `EntityRenderer` / `EntityModel` の引数変化
   - `MultiModelRenderer` 及び全 `*Layer` クラスの追従
   - `MMVertexConsumer` / `MMRenderContext` / `MMMatrixStack` / `MMPose` の API 整合
3. **CustomPayload ネットワーク**: `LMSoundPacket`, `SyncMultiModelPacket`, `SyncSoundPackPacket` を `CustomPayload + PacketCodec` に書き換え。Architectury `NetworkManager` で抽象化
4. **Resource / Pack API**: `LMPackProvider`, `LMSoundLoader`, `LMMultiModelLoader`, `LMTextureLoader`, `LMConfigLoader` の `ResourceManager` 系追従
5. **Text / Component**: `Serializer` が `RegistryWrapper.WrapperLookup` 必須
6. **NBT 永続化**: `EntityLittleMaid` 等の Entity 系で `HolderLookup.Provider` 引数化

### フェーズ 3: Mixin 再検証

- `common`: `LivingEntityAccessor` のアクセス対象メソッドが残っているか確認
- `fabric`: `ResourcePackManagerMixin` の `@At(target=...)` 生 descriptor を 1.20.5+ の `ResourcePackManager` 構造に追従
  - 仮に Mixin 戦略自体が成立しなければ NeoForge 含めて再設計が必要 (要エスカレ)

### フェーズ 4: ClassLoader / Transformer 互換性確認

- `MultiModelClassLoader` / `MultiModelClassTransformer` が Java 21 + 新 ASM で動くか実機検証
- 旧モデルパック (.class) の動的ロードが成立しなければ:
  - (a) 互換維持のための小修正で済むか
  - (b) ClassLoader 戦略の再設計が必要か
  をユーザーにエスカレ判断

### フェーズ 5: モデルパック動作確認

- LM-X や Vanilla64 等のサンプルパックでテクスチャ・モデル・サウンドが表示/再生されるか
- アーマーモデルのエンチャント光沢 (TODO に挙がっている既知不具合) は別タスク扱い

### フェーズ 6: 統合テスト

- ビルド通過 (fabric, neoforge)
- spotlessApply / checkstyle / spotbugs
- `:common:test`
- 手動動作確認:
  - モデル選択画面 (`ModelSelectScreen`)
  - サウンドパック選択画面 (`SoundPackSelectScreen`)
  - 既存パックのロード/表示/サウンド再生
  - 設定画面 (`LMMLConfig`)

## 検証方法

各フェーズで:

- `./gradlew :fabric:build` / `./gradlew :neoforge:build`
- `./gradlew spotlessApply spotlessCheck checkstyleMain spotbugsMain`
- `./gradlew :common:test`
- 実機起動: モデル/サウンドパックの読み込み確認

完了基準:

- 全プラットフォームでビルド通過
- 既存モデルパックがロード・表示できる
- 既存サウンドパックが再生できる
- 設定画面が開く
- LMML jar が LMRB 1.21.1 移植の依存として配布可能

## エスカレが必要な可能性のある設計判断

着手後に都度ユーザー判断を仰ぐもの:

- **MultiModelClassLoader / Transformer の Java 21 互換性**: 動かない場合の再設計方針
- **ResourcePackManagerMixin の継続可否**: 1.20.5+ で API が大きく変わった場合、Mixin 戦略から見直し
- **Renderer 抽象層 (MM* クラス) の維持方針**: バニラ Renderer 改修に追随するか、抽象層自体を作り直すか
- **forge → neoforge 切替で失われる Forge 固有機能の有無** (ResourcePack 系で違いが出やすい)
