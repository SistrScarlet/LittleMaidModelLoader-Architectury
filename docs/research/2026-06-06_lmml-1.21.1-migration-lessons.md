# LMML 1.21.1 移植トラブル振り返り

## 目的

LMML 8.3.1 (1.20.1) → 9.0.0 (1.21.1) 移植中に発生したトラブルを「事前にこの情報があれば最短で作業できた」観点で整理する。
LMRB 1.21.1 移植・LMRBCompat 1.21.1 移植の前準備、および将来の MC マイグレーション時の参照資料。

## 2. プラットフォーム切替の正しい手順

### NG パターン (今回の失敗)

`git mv forge/ neoforge/` でディレクトリをリネーム。

**問題**: 1.20.1 ブランチからの cherry-pick 運用と相性が悪い。1.20.1 側で `forge/` を触る修正を 1.21.1 にぶつけると毎回 rename 由来のコンフリクトが出る。

### 正しいパターン

1. `forge/` は **残置** (HEAD のまま)
2. `neoforge/` を **新規追加**
3. `settings.gradle` から `include("forge")` を削除し `include("neoforge")` を追加
4. `gradle.properties` の `enabled_platforms` から `forge` を除外

これで Gradle は forge を無視。forge コードは参照用として残り、cherry-pick 時の参照対象としても使える。

## 3. Gradle 構成のハマりどころ

### Gradle wrapper を上げる前にエラーが出る

Java 21 環境では Gradle 7.4 は Groovy class major version 不一致で起動しない。
`gradle-wrapper.properties` の `distributionUrl` を 8.x に書き換えてから操作。

### neoforge の mappings 二重定義

root `build.gradle` の `subprojects { dependencies { mappings ... } }` と
neoforge の `mappings loom.layered { ... }` が衝突して
`Configuration 'mappings' must only have 1 dependency` エラー。

**回避**: neoforge/build.gradle の dependencies ブロック直前に
```groovy
configurations.mappings.dependencies.clear()
```
を入れてから layered mappings を定義。

または subprojects 側で yarn 単体定義をやめて、各プラットフォームに分散する手もあり (好み)。

### neoforge build.gradle の必須変更点

- `architectury { neoForge() }` (forge() ではない)
- `developmentNeoForge.extendsFrom common` (developmentForge ではない)
- `shadowBundle` configuration (shadowCommon ではない)
- `neoForge "net.neoforged:neoforge:${rootProject.neoforge_version}"`
- `mappings loom.layered { yarn + yarn-mappings-patch-neoforge }`
- `transformProductionNeoForge` で common を引き込む
- shadow plugin で `archiveClassifier = "x"` を使う (旧 `classifier "x"` は削除)
- maven リポジトリに NeoForged を追加

### neoforge.mods.toml

旧 forge mods.toml と非互換な点:
- ファイル名が `neoforge.mods.toml` (mods.toml ではない)
- `modId = "neoforge"` (forge ではない)
- `versionRange = "[21.1,)"` (NeoForge バージョン)
- 依存に `type = "required"` を使う (旧 `mandatory = true` ではない)
- Mixin 設定は `[[mixins]] config = "..."` セクションで明示 (forge では build.gradle の `loom { forge { mixinConfig ... } }` だったが neoforge ではここ)

### NeoForge 21.1 プラットフォーム入口クラスの正しい形 (Architectury 13)

旧 `LMMLForge.java` の機械置換 (`net.minecraftforge.*` → `net.neoforged.*`) では足りない。Mod 構造そのものが変わっている。

**変更点まとめ**:

| 旧 (Forge / Architectury 11) | 新 (NeoForge 21.1 / Architectury 13) |
|------|------|
| `public LMMLForge()` 引数なし | `public LMMLNeoForge(IEventBus modBus, ModContainer container)` |
| `FMLJavaModLoadingContext.get().getModEventBus()` | コンストラクタ引数の `modBus` を直接使う |
| `EventBuses.registerModEventBus(MODID, modBus)` | **不要** (Architectury 13 が `ModList.get().getModContainerById(MODID).map(ModContainer::getEventBus)` で自動取得) |
| `ModLoadingContext.get().registerExtensionPoint(ConfigScreenHandler.ConfigScreenFactory.class, ...)` | `container.registerExtensionPoint(IConfigScreenFactory.class, (mc, parent) -> ...)` |
| `net.minecraftforge.client.event.EntityRenderersEvent` | `net.neoforged.neoforge.client.event.EntityRenderersEvent` |
| `net.minecraftforge.event.AddPackFindersEvent` | `net.neoforged.neoforge.event.AddPackFindersEvent` |
| `net.minecraftforge.fml.event.lifecycle.FMLCommonSetupEvent` | `net.neoforged.fml.event.lifecycle.FMLCommonSetupEvent` |
| `net.minecraftforge.fml.common.Mod` | `net.neoforged.fml.common.Mod` |
| `ConfigScreenHandler.ConfigScreenFactory` の screen factory | `IConfigScreenFactory#createScreen(ModContainer, Screen) -> Screen` (`net.neoforged.neoforge.client.gui.IConfigScreenFactory`) |

**Architectury 13 の重要な仕様変更**:
- `EventBuses.registerModEventBus` 呼び出しは neoforge では不要 (ModContainer 自動取得に切り替わった)
- ただし `dev.architectury.platform.forge.EventBuses` クラス自体は `architectury-neoforge` jar に残っており、import パスは紛らわしい。**そもそも呼ばないのが正解**
- `dev.architectury.platform.hooks.EventBusesHooks` が内部実装

**Mod コンストラクタの正しいシグネチャ** (NeoForge 21.1):

```java
@Mod(LMMLMod.MODID)
public class LMMLNeoForge {
    public LMMLNeoForge(IEventBus modBus, ModContainer container) {
        LMMLMod.init();

        container.registerExtensionPoint(
                IConfigScreenFactory.class,
                (mc, parent) -> AutoConfig.getConfigScreen(LMMLConfig.class, parent).get());

        modBus.addListener(this::modInit);
        modBus.addListener(this::clientInit);
        modBus.addListener(this::rendererInit);
        modBus.addListener(this::packInit);
    }
    // ... handlers as before
}
```

### Architectury 13 の Platform predicate の意味論変化 (要注意)

| Predicate | 1.20.1 (Architectury 11) | 1.21.1 (Architectury 13) |
|-----------|------|------|
| `Platform.isForge()` | Forge のみ true | **`isForgeLike()` の alias**: Forge + NeoForge 両方で true (`@Deprecated(forRemoval = true)`) |
| `Platform.isNeoForge()` | (存在しない) | NeoForge でのみ true |
| `Platform.isMinecraftForge()` | (存在しない) | Forge でのみ true |

**影響**: `Platform.isForge()` を使っている既存コードは NeoForge でも分岐に入る。意味的に問題なければ放置可だが、コメント整合性チェックは必要 (例: 「Forge の ModuleClassLoader が...」というコメントが NeoForge 由来エラーまで含めて読めるか)。
**推奨**: 新規コードでは `Platform.isForgeLike()` を使い、本当に Forge のみが必要な箇所では `Platform.isMinecraftForge()` を使う。

## 4. 1.20.1 → 1.21.1 Mojang API Breaking Changes チートシート

エラー件数の多い順 (今回の実例ベース)。

### 機械的置換可能 (sed/Edit でほぼ一発)

| API | 旧 | 新 |
|-----|----|----|
| Identifier | `new Identifier(ns, path)` | `Identifier.of(ns, path)` |
| EntityType.Builder | `.setDimensions(w, h)` | `.dimensions(w, h)` |
| LivingEntity | `entity.getItemsEquipped()` | `entity.getEquippedItems()` |
| EquipmentSlot | `slot.getType() == EquipmentSlot.Type.ARMOR` | `slot.isArmorSlot()` |
| Element / ParentElement | `mouseScrolled(x, y, amount)` | `mouseScrolled(x, y, horizontalAmount, verticalAmount)` (引数追加) |
| Sound コンストラクタ | `new Sound(String, ...)` | `new Sound(Identifier, ...)` |
| Shadow plugin | `classifier "x"` | `archiveClassifier = "x"` |

### 構造変更 (個別判断が必要)

| API | 内容 |
|-----|------|
| `EntityModel#render` | 引数 (matrices, vertices, light, overlay, **r, g, b, a**) → (matrices, vertices, light, overlay, **int color** (ARGB)) |
| `VertexConsumer#vertex` | 14 引数 (x,y,z, r,g,b,a, u,v, overlay,light, nx,ny,nz) → 11 引数 (x,y,z, **color**, u,v, overlay,light, nx,ny,nz) ARGB int |
| `LivingEntityRenderer#setupTransforms` | 引数 5 → 6 個 (末尾に `float scale` 追加) |
| `ItemRenderer.getArmorGlintConsumer` | 4 引数 → 3 引数 (第3引数 false 削除) |
| `Entity#createSpawnPacket` | 引数なし → `EntityTrackerEntry trackerEntry` 引数追加 |
| `InventoryScreen.drawEntity` | (ctx, x, y, size, mouseX, mouseY, entity) 7 引数 → (ctx, x1, y1, x2, y2, size, yOffset, mouseX, mouseY, entity) 10 引数 (矩形指定型) |
| `ArmorItem#getMaterial().getName()` | String → `RegistryEntry<ArmorMaterial>` 化、`.getKey().map(k -> k.getValue().getPath())` で取得 |

### 廃止された API (代替が必要 / 機能ロス)

| API | 状況 | 代替 |
|-----|------|------|
| `LivingEntity#getDimensions(EntityPose)` | **final 化** | `EntityType.Builder` で固定値 / `EntityAttachments` / Mixin で final 突破 |
| `LivingEntity#getActiveEyeHeight` | 削除 | `EntityType.Builder.eyeHeight(...)` または `EntityAttachments.EYE_HEIGHT` |
| `LivingEntity#getMountedHeightOffset` | 削除 | `EntityAttachments.PASSENGER` |
| `LivingEntity#getHeightOffset` | 削除 | `EntityAttachments` 経由 |
| `LivingEntity#getRoll` | 削除 | (代替不明、固定値 0F で対応) |
| `ResourcePack#isAlwaysStable` | 削除 | (削除のみ) |
| `ResourcePack#getName` | 改名 | `getId()` |
| `Pack.Info` 系の `PackResourceMetadata(Text, int)` | 廃止 | `ResourcePackInfo(id, name, source, knownPack)` レコード |

### CustomPayload 化 (Network 全面再設計)

1.20.5+ で `FabricPacket` + `PacketByteBuf` 直書きが完全廃止。
書き換え手順:

1. パケットクラスを `record implements CustomPayload` に再設計
2. `CustomPayload.Id<T> ID = new CustomPayload.Id<>(Identifier.of(...))` を定義
3. `PacketCodec<RegistryByteBuf, T> CODEC` を定義
   - フィールド少 (≤6): `PacketCodec.tuple(codec1, getter1, codec2, getter2, ..., Constructor::new)`
   - フィールド多 / 入れ子: `PacketCodec.of((packet, buf) -> {...write...}, buf -> {...read; return new T(...);})`
4. `getId()` で ID を返す override
5. Networking クラスで:
   - `NetworkManager.registerS2CPayloadType(ID, CODEC)` を **サーバ側でも** 呼ぶ (Architectury 13 仕様)
   - `NetworkManager.registerReceiver(Side, ID, CODEC, receiver)`
6. 送信は payload オブジェクトを `sendToServer(payload)` / `sendToPlayers(players, payload)`
7. 受信ハンドラのシグネチャは `(T payload, NetworkManager.PacketContext ctx) -> void`

### Resource / Pack API

```java
// 旧
ResourcePackProfile.create(
    String name, Text title, boolean alwaysEnabled,
    ResourcePack.Factory factory, ResourceType type,
    InsertionPosition position, ResourcePackSource source);

// 新
ResourcePackProfile.create(
    ResourcePackInfo info,           // new ResourcePackInfo(id, name, source, Optional<KnownPack>)
    ResourcePackProfile.PackFactory factory,  // 2 abstract methods: open + openWithOverlays
    ResourceType type,
    ResourcePackPosition position);  // new ResourcePackPosition(alwaysEnabled, InsertionPosition, required)
```

`PackFactory` は functional interface ではない (2 abstract method) ため、明示的な匿名クラス実装必須。

## 5. 推奨される進め方 (作業効率最大化)

### 順序

1. **依存バージョン確定** (本書のマトリクス参照)
2. **ビルド環境セットアップ** (フェーズ 1)
   - gradle.properties / wrapper / shadow plugin / Loom plugin
   - forge 残置 + neoforge 新規追加
   - `./gradlew projects` で評価通過確認 (コンパイルはまだ)
3. **compile エラー全件取得 → カテゴリ分け**
   ```bash
   ./gradlew :common:compileJava --no-daemon 2>&1 | \
     grep -E "error:" | sed -E 's/.*error: //' | sort | uniq -c | sort -rn
   ```
4. **機械的修正から優先**
   - Identifier 一斉置換 (sed で OK)
   - mouseScrolled 引数追加
5. **構造変更**
   - Network → CustomPayload
   - Resource Pack
   - Renderer
6. **機能ロス受容と TODO 化**
   - EntityAttachments 系、`getDimensions` 等
7. **fabric / neoforge 個別**
   - fabric: Mixin 再検証
   - neoforge: プラットフォーム入口クラス全面書き換え

### コミット分割

機械的修正 / 構造変更 / 機能ロス受容 はそれぞれコミットを分けると、後でレビューしやすく cherry-pick も柔軟。

実際にやった分割:
- `2-1` Identifier + mouseScrolled (機械的)
- `2-2` Renderer 系部分追従
- `2-3` Network CustomPayload 化
- `2-4` Resource / Pack API
- `2-5` Entity 系 + 個別 API
- `2-6` 残り API 追従 (common compileJava 通過)
- `2-7` NeoForge プラットフォーム入口 (NeoForge 21.1 API 化、:neoforge:build 通過)

## 6. 情報源とアクセス手段

### Yarn mapping を確認したい

```bash
gh api repos/FabricMC/yarn/contents/mappings/net/minecraft/<Path>.mapping?ref=1.21.1 \
  | python3 -c "import json,sys,base64; d=json.load(sys.stdin); print(base64.b64decode(d.get('content','')).decode())"
```

`-jq .content` で取得した base64 を decode する形でも可。

### Architectury API のソースを確認したい

```bash
gh api repos/architectury/architectury-api/contents/common/src/main/java/dev/architectury/<Path>.java?ref=1.21 \
  --jq .content | base64 -d
```

ブランチは `1.21` 等 MC バージョン名 (1.21.1 ブランチは存在しない、1.21 を使う)。

### 実例コードを探したい

```bash
gh search code "ResourcePackProfile.create" --extension java --limit 5
```

## 7. ツール使用上のハマりポイント

### Edit ツールは Read 必須

新規ディレクトリ作成 (git mv 直後など) でも、対象ファイルを **必ず Read してから** Edit。
今回 `gradle-wrapper.properties` の最初の Edit が Read 前で失敗 → 後続に気付かず Gradle 8.12 が反映されたつもりで実行 → エラー、というロスがあった。

並列 Edit を投げる時、1 つでも失敗すると後続ツールの結果が読みにくくなる。

### Bash の cd は session 持続するが不安定

`cd /path && command` の chain を 2 つ並列で投げると、後者は cd 結果を引き継がない (session が別だから)。
別ディレクトリの作業は **毎回 `cd` から書く** か絶対パスで完結させる。

## 8. LMRB / LMRBCompat 着手前にやるべきこと

LMRB は LMML より影響範囲が広い (DataComponents 化が直撃):

- 本書のチートシート (4 章) で LMRB 計画書フェーズ 2 の各項目を再確認
- LMML 9.0.0 jar を mods/ に配置できる状態にしてから着手
- `ItemStack#getTag()` 等の DataComponents 化は **LMML には影響なかった** ため未検証。LMRB で初めて出会う
- Mixin Accessor の `_LM` サフィックスメソッド群は対象メソッドが残っているか個別確認
- GameTest 全件移植は当該ストラクチャーの NBT 形式変化も影響する可能性

LMRBCompat は LMRB が安定してから。外部 Mod (Twilight Forest 等) の 1.21.1 対応状況も依存する。

## 9. 今回の機能ロスのリスト (要後続対応)

LMML 9.0.0 で **失われた機能** (TODO で明示済み):

| 失った機能 | 影響 |
|-----------|------|
| MultiModelEntity の動的 dimensions | メイドさんモデルサイズに応じた hitbox 変化が無効 |
| 動的 EyeHeight | カメラ視点高さがモデルサイズに追従しない |
| 動的 mount / passenger offset | 騎乗時のオフセットがモデルに合わない |
| EntityCaps の roll / mountedYOffset / YOffset | カスタムモデル描画でこれらを参照していた挙動が固定値 0 |

復元には `EntityAttachments` の調査 / Mixin での final 突破 / 代替設計のいずれかが必要。
要設計判断としてユーザーエスカレ案件。
