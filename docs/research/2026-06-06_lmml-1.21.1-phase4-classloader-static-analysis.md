# LMML 1.21.1 移植 フェーズ 4 ClassLoader/Transformer 静的解析

## 目的

フェーズ 4 の本番作業 (実機検証) に入る前に、`MultiModelClassLoader` と `MultiModelClassTransformer` を Java 21 + NeoForge 21.1 / Fabric 0.16 の新 ClassLoader 制約下で読み、静的に潰せる懸念点とリスク評価を整理する。

実機検証で当たる前に頭に入れておきたい論点のチートシート。

## 対象

- `common/src/main/java/net/sistr/littlemaidmodelloader/resource/classloader/MultiModelClassLoader.java` (96 行)
- `common/src/main/java/net/sistr/littlemaidmodelloader/resource/classloader/MultiModelClassTransformer.java` (354 行)

## 静的検証で確認できた前提

| 前提 | 検証 |
|------|------|
| ASM バージョン | NeoForge 21.1.233 / Fabric 0.16 同梱の ASM 9.6 で Java 21 (class file v65) サポート済み |
| `Platform.isForge()` の挙動 | Architectury 13 では `@Deprecated` だが `isForgeLike()` を返すため **NeoForge でも true**。`MultiModelClassLoader#loadClass` の forge 用 workaround は NeoForge でも引き続き動く |
| `Platform.isFabric()` の挙動 | NeoForge 上では false → Transformer は Mojang 名前空間 (`net/minecraft/world/entity/Entity`) を選択。NeoForge 21.1.x は Mojang Official Mappings 採用のため正しい |
| ASM bytecode 入出力 | 旧 model pack の class file (Java 6-8 / v50-52) と新 MC class file (Java 21 / v65) は ASM 9.6 で両方読み書き可 |

## 懸念点

### A. HIGH: `ClassWriter.COMPUTE_FRAMES` がスーパークラス解決に失敗する可能性

`MultiModelClassTransformer#transform` は `ClassWriter(COMPUTE_FRAMES | COMPUTE_MAXS)` を使う (320 行)。

`COMPUTE_FRAMES` はスタックマップ計算のため `ClassWriter#getCommonSuperClass(String, String)` を呼ぶ。default 実装は `Class.forName(name, false, getClassLoader())` で実クラスをロードし、共通スーパー型を計算する。

```java
// ASM 9.6 ClassWriter#getCommonSuperClass デフォルト実装 (要旨)
ClassLoader classLoader = getClassLoader();
Class<?> class1 = Class.forName(type1.replace('/', '.'), false, classLoader);
Class<?> class2 = Class.forName(type2.replace('/', '.'), false, classLoader);
...
```

ここで使われる ClassLoader はデフォルトで `ClassWriter` 自身を定義したクラスローダー = LMML の mod ClassLoader。

**問題シナリオ**:

1. 旧 model pack の class が `mmmlibx/lib/multiModel/model/mc162/ModelLittleMaidBase` を継承
2. Transformer が `net/sistr/littlemaidmodelloader/maidmodel/ModelLittleMaidBase` に書き換える
3. `COMPUTE_FRAMES` がこの新親クラスを `Class.forName` で取得しようとする
4. LMML mod ClassLoader からは見える → OK
5. しかし旧 model pack class 自身が `net/minecraft/world/entity/Entity` を field 型などで参照する場合、`Class.forName("net.minecraft.world.entity.Entity", false, lmmlClassLoader)` を解決する必要がある
6. NeoForge の TransformingClassLoader / Fabric の KnotClassLoader 階層では一般に MC クラスは委譲可能 → 通る見込み
7. **ただし Java 21 の Module Layer 経由でアクセスする場合、`Class.forName` で `Module#isExported` 検査に引っかかる余地あり**

**実機検証ポイント**:
- `:fabric:runClient` / `:neoforge:runClient` で旧 model pack をロードした際、`COMPUTE_FRAMES` 中で `ClassNotFoundException` または `IllegalAccessError` が起きないか
- 落ちた場合の対応: `ClassWriter` をサブクラス化して `getCommonSuperClass` を override、`MultiModelClassLoader` 自身を経由して解決させる

```java
ClassWriter writer = new ClassWriter(COMPUTE_FRAMES | COMPUTE_MAXS) {
    @Override
    protected String getCommonSuperClass(String type1, String type2) {
        try {
            return super.getCommonSuperClass(type1, type2);
        } catch (TypeNotPresentException | RuntimeException e) {
            // フォールバック: java/lang/Object に倒す
            return "java/lang/Object";
        }
    }
};
```

これは事前に入れておく価値あり (実害なし、保険として機能する)。

### B. MEDIUM: `URLClassLoader` の親ローダー経由での MC クラス参照

`MultiModelClassLoader.<init>` は親に `MultiModelClassLoader.class.getClassLoader()` を渡す (LMML 本体 ClassLoader)。

旧 model pack class を define した後、その class が referencer として `net/minecraft/class_1297` / `net/minecraft/world/entity/Entity` を持つ。
JVM は defining classloader = `MultiModelClassLoader` から resolve を試み、見つからなければ parent = LMML mod ClassLoader へ委譲する。

Fabric (KnotClassLoader): 同一 mod loader 内なので通る。
NeoForge (TransformingClassLoader): module 境界を跨ぐ可能性あり。NeoForge 21.1 では mod は `MOD` layer に属し、MC は `GAME` layer。`MOD` → `GAME` は read 可能なので通常は OK。

**実機検証ポイント**:
- 旧 model pack class の method 呼び出し時に `NoClassDefFoundError` が出ないか
- LinkageError / IllegalAccessError も警戒

### C. MEDIUM: `defineClass` の package sealing 検査

Java 9+ では `Package.isSealed()` の概念があり、同じ package が複数 classloader で定義されると `LinkageError` が出る場合がある。

`MultiModelClassLoader` が define する class の package は以下を想定:
- `mmmlibx/lib/...` (旧 LittleMaid モデル独自)
- `firis/lmmm/...` (FIRIS 系)
- `net/blacklab/lmr/...`
- デフォルト package (`MMM_*`)

これらは LMML 本体や MC とは重複しない (mod ID として独立) → ✓ 安全。

ただし `addTransformTarget` で `PACKAGE_STRING = "net/sistr/littlemaidmodelloader/maidmodel/"` への置換が起きる。これは **置換 (参照書き換え)** であって `defineClass` の対象ではない。LMML 本体 ClassLoader 経由で resolve される → ✓ 安全。

### D. MEDIUM: `loadClass` の Forge workaround の動作維持

```java
@Override
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    if (Platform.isForge()) {
        try {
            return super.loadClass(name, resolve);
        } catch (IndexOutOfBoundsException e) { // ForgeのModuleClassLoaderがsubstringで落ちた場合
            if (name.lastIndexOf('.') == -1) {
                Class<?> c = findClass(name);
                ...
```

`Platform.isForge()` が NeoForge でも true なため、この workaround は NeoForge でも有効。
NeoForge の TransformingClassLoader が、デフォルト package のクラス名 (ドット無し) を `name.substring(0, name.lastIndexOf('.'))` で処理する箇所が残っているかは要実機確認。

**実機検証ポイント**:
- 旧 model pack に default-package class (`MMM_EntityCaps` 等) が混じっていた場合に `IndexOutOfBoundsException` が依然として発生するか
- 発生しない場合は workaround を Fabric 同様の単純な `return super.loadClass(name, resolve)` に統一して TODO 整理

### E. LOW: legacy class が削除済み Java API を参照していた場合

旧 model pack (1.6.4 〜 1.10.2 時代) は Java 6-8 でビルドされている。Java 21 で削除されたもの:

- `sun.misc.Unsafe` の一部 method (一部はモジュール export 外)
- `java.applet.*` (1.20 以前で削除)
- `javax.security.cert.*` (Java 15 で削除)

ただし model pack の用途 (描画ロジック) でこれら API を呼ぶ蓋然性は極めて低い。実機で `NoSuchMethodError` / `NoClassDefFoundError` が出るまで顕在化を待つで十分。

### F. LOW: `parallelStream()` の使用箇所

`fields.parallelStream()` / `methods.parallelStream()` / `localVariables.parallelStream()` を transformer 内で使用 (181/195/201 行)。Java 21 の `ForkJoinPool.commonPool()` を共有するため、デッドロックリスクは無いが、ASM の `ClassNode` 構造体が thread-safe ではない点に留意。
ただし各 stream は独立した `FieldNode`/`MethodNode` を処理するだけで、共有 mutable state は `AtomicBoolean changed` のみ。**OK**。

### G. LOW: `Platform.isForge()` の deprecation 警告

ビルド時に `@Deprecated(forRemoval = true)` 警告が出るが、Architectury 13 系では引き続き機能する。`isForge()` の意味論が forge-only ではなく forgeLike (forge + neoforge) になっているため、コメント `// ForgeのModuleClassLoaderがsubstringで落ちた場合` は **「Forge 系」と読み替える** ことが正しい。

**フォローアップ TODO 候補**: `Platform.isForge()` → `Platform.isForgeLike()` への置換 (意味論を明示化、deprecation 警告も解消)。

## 実機検証の最短手順 (フェーズ 4 本番)

1. **runClient 起動**
   - `./gradlew :fabric:runClient` / `./gradlew :neoforge:runClient`
2. **LMMLResources/ にサンプル model pack 配置**
   - 既存の動作実績パック (LM-X / Vanilla64 系) を 1 つ
3. **ログで以下のキーワードを grep**
   - `NoClassDefFoundError`
   - `LinkageError`
   - `IllegalAccessError`
   - `IndexOutOfBoundsException` (forge workaround の trigger)
   - `ClassNotFoundException` (transformer の `Class.forName` 由来も含む)
4. **失敗時の典型対応**
   - `COMPUTE_FRAMES` 落ち → 上記 A 節の `getCommonSuperClass` override 適用
   - default package class 落ち → D 節の workaround を強化または別経路で findClass
   - `IllegalAccessError` → module export 設定 (NeoForge `module.add-opens` 等) を mods.toml で要求

## 静的解析の結論

- **クラス本体の構造** は Java 21 でそのまま動く設計。書き換え必須箇所は **無い**。
- **A 節の `COMPUTE_FRAMES` 解決失敗** が唯一の HIGH リスクで、保険として `getCommonSuperClass` の override を入れておく価値あり。**それ以外は実機で当たって初めて顕在化する** タイプのリスク。
- フェーズ 4 で本来必要なのは「実機起動 → エラー観察 → 対応」というループ。事前に書き換えるべきコードは保険の `ClassWriter` override 程度。
